# Architecture

## Pattern and scope

Use a small layered architecture with an application controller in each Chrome execution context. Plain functions and ES modules provide the boundaries; there is no DI container, event bus, repository interface hierarchy, or UI framework. Modules depend inward on shared types and validation. Browser and network effects stay at the edges.

```text
popup.ts                 background.ts              offscreen.ts
DOM, settings form       Chrome API coordination    Sequential upload runner
PDF selection            Trusted token storage      Source retrieval + multipart
       │                       │                         │
       └───── control messages ┴──── control messages ──┘
       │                                                 │
       └──────────── data/jobs.ts (IndexedDB) ────────────┘
                         │
                    shared/ types
                    services/ API + PDF source fetch
```

The popup stages selected PDF blobs in IndexedDB and asks the background worker to process them. The worker creates one offscreen document using the `BLOBS` reason. Chrome messages carry control data and small status objects, never binary files. The offscreen runner reads blobs directly and uses `FormData` for upload. This avoids JSON serialization and base64 memory overhead.

The toolbar action opens the popup without staging a new job. Only **Aktuelle PDF hochladen**, file selection/drop, or the window action starts a new batch. Saving settings and granting local file access do not start uploads. Reopening the popup can resume jobs already queued by an earlier explicit action; accepted and uncertain results disable the matching current-tab action, while failed jobs require an explicit retry.

The Chrome service worker owns connection settings, optional permissions, badges, and offscreen creation/closure. The popup stores its display preference separately in trusted local storage. The offscreen document owns requests because Chrome can terminate a worker whose fetch waits more than 30 seconds. It closes after the upload queue and bounded import checks are finished. A popup poll refreshes visible status every 500 ms only while that popup exists. Polling ends when the popup closes.

## PDF response capture and display

On Chrome 151 or newer, the manifest routes top-level and embedded PDF responses to `capture.html`. The handler calls `chrome.mimeHandler.getStreamInfo()` and consumes its extension-owned stream URL once with `Response.blob()`. The browser assembles the received body for display and upload, including responses to authenticated POST requests and single-use links.

The handler embeds a local Blob URL in an iframe. The inner handler recognizes its own extension origin and calls `abortAndFallbackToNativeHandler()` on that Blob so Chrome displays its native viewer. A fallback reload can only reread the local preview. The outer handler preserves the portal address and the original document bytes. In a direct PDF tab it takes initial keyboard focus and handles Ctrl+S or Command+S with a named download of the same Blob. A full-page portal embed can receive that shortcut through an isolated script attached to its host document. The script checks the visible viewer and keyboard focus before forwarding the save gesture through a document-scoped port. Chrome's native toolbar remains available after the user focuses the PDF contents.

PDF display does not depend on upload eligibility or successful cache storage. PDFs above 50 MiB can still be viewed, and cache errors are displayed alongside the viewer. Only valid PDFs within the upload limit receive a cached body and a SHA-256 content fingerprint. Chrome can omit `Content-Disposition` from the MIME handler stream. With existing HTTP(S) host access, a non-blocking `webRequest` listener keeps only that header and the matching tab/URL in service-worker memory for PDF document responses. The capture page consumes the matching record without replaying the request. Local files retain their filename; captured and retrieved PDFs use the response filename, a PDF URL basename or an explicit filename parameter, then the source host and short content fingerprint.

Chrome 116 remains the minimum supported version. Older versions can retrieve a top-level HTTP(S) PDF by GET or read an allowed file URL. A previously opened document from an expired URL can be saved in its existing viewer and selected locally. Blob URLs and embedded PDFs require a matching capture.

## Data and lifecycle

- `chrome.storage.local`: normalized base URL and API token, limited to trusted extension contexts. Settings are not synced to a Google account.
- IndexedDB database `paperless-upload` version 3 retains the `jobs` and `files` stores and migrates version 2 captures under their original numeric keys.
- IndexedDB `sources` stores a capture under the Chrome document ID of its handler, with an index on tab ID. Metadata includes the original URL, name, time, fingerprint, and an optional Blob or error. Loading records have a temporary fingerprint. The cache holds up to 25 bodies and 512 MiB, evicting the oldest bodies first. On tab load completion, startup and discovery, the worker uses `runtime.getContexts()` to discard records for viewers that have closed. A fragment change preserves the same document ID. Closing the tab clears its captures.
- IndexedDB `jobs`: metadata and status for the latest batch. Local file selection is bounded to 512 MiB in total; a window batch is bounded by the PDF tabs in that window. Every new job is bound to the normalized server URL captured when the user starts the batch, without storing credentials. An unbound queued job from an older version or a mismatched destination fails before any upload. Source jobs include the original URL, tab ID, and capture fingerprint when available. Captured document identity combines URL and fingerprint: identical content at the same URL is preserved across tabs, while a different response at the same POST endpoint can be uploaded separately. Uncaptured sources retain URL-based identity. PDF page fragments are excluded from identity.
- IndexedDB `files`: temporary blobs, deleted after each terminal result. Metadata queries do not load the file bodies. Starting another batch clears old results and leftover blobs in one transaction while retaining accepted jobs that still need an import check.
- Job transitions: `queued → downloading → uploading → accepted | failed | uncertain`; local files and staged captured PDFs skip `downloading`, ordinary web pages end as `skipped`.
- When a runner starts with no current owner, it marks previously interrupted downloads as failed and previously interrupted uploads as uncertain. It does not repeat either request. Still-queued jobs have never started an upload and can proceed.

The queue is deliberately one batch at a time. IndexedDB checks and stages each batch within one read/write transaction, preventing overlapping popups from adding conflicting batches. Staging copies matching captured blobs from `sources` into `files` in that transaction, so subsequent cache eviction, tab closure, or navigation does not invalidate queued uploads. A matching loading, error, or unavailable capture record fails with an explanation rather than falling back to another GET. When staging a window batch, confirmed and unconfirmed results for matching document identities are retained; only new or explicitly retried failed documents are queued. Offscreen lifecycle mutations are serialized. There is no retry queue or upload history feature.

The popup snapshots the current window to offer local-file access. The worker queries that window again for a batch and checks host permissions. Both actions use the same tab detector. A direct capture must match the tab URL. For an embedded capture, the detector inspects the visible iframe, embed or object in the top-level document and compares its document or element URL to the captured URL. An opener-created `about:blank` tab is eligible through the same check. Pages with several live captures are skipped. Uncaptured web and file tabs are inspected for their document MIME type. The worker checks at most eight tabs concurrently, preserves their order, and stages matching document identities once.

The popup can explicitly dismiss failed/skipped jobs, completed imports, and transient notices. Dismissal checks for active jobs and removes eligible records and blobs in one IndexedDB transaction; it only marks accepted records as hidden, leaves uncertain outcomes intact, and refreshes the toolbar badge. Non-PDF responses remain visible as skipped and allow an explicit retry. The runner persists terminal state and removes the staged blob in the same transaction. It can retry that write once, but never the POST. The toolbar badge is advisory and cannot stop the queue. A start signal arriving during a queue read forces a fresh read before the runner sleeps or exits.

The window action scans and stages the current window's PDFs in one explicit gesture. Accepted/uncertain jobs are preserved to prevent duplicate uploads. The popup shows the current-tab action only for a matching capture record or a top-level PDF MIME type. The check reads the active document without making a source request. Loading or unavailable capture states explain why the action is disabled. Each row shows a single status and a labelled document link where available. Positive results disappear after the chosen display duration (eight seconds by default, or never; hovered and focused rows stay visible), while pending imports, failures and uncertain outcomes remain visible. Filtering rows does not change stored jobs, polling or duplicate protection.

## Security and permissions

Required permissions are `activeTab`, `tabs`, `scripting`, `storage`, `offscreen`, and `webRequest` for the original PDF filename. `tabs` provides the URLs needed to request scoped permissions before the window action starts; `scripting` checks the top-level document type and URL and, for a captured embedded PDF, the visibility and URL of its embedding element. The MIME handler receives top-level and embedded PDFs as they open, independently of those optional host grants, and only stores their data locally until an explicit upload action. The full-page save shortcut uses the existing website access. Its key listener is removed when the viewer disconnects. Optional broad HTTP and HTTPS host access is requested once directly from the save gesture, or the first window-upload gesture for existing setups. The popup checks existing grants and reuses them, updating on permission changes. Chrome retains these grants until revoked in its extension settings. Replacing a server only removes a previous scoped server grant if no broad grant for its scheme covers it. Local `file:` access is optional and separate.

Uploaded PDFs are validated by byte signature in the first 1 KiB and bounded to 50 MiB. The GET fallback enforces that limit while reading; response capture assembles a Blob for display before applying the upload/cache limit. MIME types and filenames alone do not establish PDF content. All selected files are validated before a batch is staged. The browser's file selection already provides local file access, so it does not need broad filesystem access.

Only the Paperless API services send the `Authorization: Token` header. Source requests carry the source site's normal browser credentials, never the Paperless token; captured bytes require no new source request. API requests omit browser cookies and reject redirects. Source URLs may contain sensitive query parameters and remain local in capture metadata and the latest batch; they are not logged or sent to a third party. The token is not stored in either IndexedDB job or capture records. All UI content is inserted with `textContent`, not interpreted as HTML. The manifest enforces local-only scripts and styles, permits Blob frames for the native PDF viewer, and prohibits objects. No remote code or runtime dependencies are used.

Connection verification uses `GET api/profile/`, an authenticated endpoint that does not require access to documents. The public `api/` root redirects to Swagger in current Paperless versions and cannot establish connectivity or token validity. Only a matching profile token confirms the connection; the profile response is discarded without being stored, logged, or sent to the popup. Manual redirect handling reports a redirected API separately from network errors without following it or forwarding credentials.

HTTP is allowed for self-hosted local servers with an explicit UI warning. The extension cannot fix invalid TLS certificates or bypass server authentication gateways. It does not encrypt the locally stored token; Chrome profile access grants access to extension storage. This is described plainly rather than hidden behind ineffective client-side encryption.

## Automatic import confirmation

Accepted jobs retain the upload response's task UUID, normalized server URL, and start time in `importTask`; no token is added to IndexedDB. Import results are separate and never change upload acceptance. The offscreen runner drains queued uploads first, then checks pending imports automatically every five seconds or transient failures every 15 seconds for about two minutes from acceptance. A new upload wakes a sleeping runner. The first status lookup is still allowed after a long upload queue; subsequent checks obey the persisted deadline. Terminal results, permission errors, unsupported endpoints and malformed responses stop checking. Expiry produces a visible unavailable result. The runner continues when the popup closes and resumes unfinished work on startup or popup initialization; it closes when there is no upload or import work. Each GET has a 15-second timeout. Settings are reread before each check, and a server URL mismatch is rejected before sending any request. Transactional updates reread the job so a late GET cannot recreate a replaced batch.

`services/import-task.ts` queries `api/tasks/?task_id=...`, validates the matching ID, and supports the legacy array and API v10 paginated result shapes. Document IDs must be positive safe integers. Success and duplicate links use only the saved server base and a validated ID. Duplicate classification uses structured fields (`related_document` on legacy failures or `result_data.duplicate_of`), never arbitrary error text. Missing permissions and malformed responses are displayed as unavailable without undoing upload acceptance; missing task records and temporary network/server errors are retried only within the time budget. After an unavailable result stops automatic checking, the user can restart status checks for the same task on the configured server without sending another upload. These contracts are based on the [Paperless API documentation](https://github.com/paperless-ngx/paperless-ngx/blob/dev/docs/api.md), [legacy serializer](https://github.com/paperless-ngx/paperless-ngx/blob/v2.20.15/src/documents/serialisers.py), and [current task model](https://github.com/paperless-ngx/paperless-ngx/blob/dev/src/documents/models.py).

## Verification boundaries

Unit tests cover validation and network contracts. Chromium tests cover actual extension execution, IndexedDB cleanup, messaging, multipart transfer, sequential batches, continued uploads after closing the UI, and interrupted-upload recovery. Popup tests verify that opening and saving settings do not request or upload a source before the explicit current-tab action. Toolbar cases open GET, POST-generated, and single-use PDFs in Chrome's viewer, trigger the actual extension action, and check source request counts and uploaded bytes across distinct source/server hostnames. The window test uses extensionless PDF tabs, an ordinary HTML page, duplicate URLs, and a second browser window. It also verifies that repeated window actions preserve accepted and unconfirmed uploads without another POST. Test-only Chrome management APIs pregrant the optional web permission; accepting Chrome's native permission dialog remains a manual check. A local fixture API provides deterministic responses without real credentials or production data. These checks do not establish compatibility with every PDF provider or prove import completion on a particular Paperless installation.
